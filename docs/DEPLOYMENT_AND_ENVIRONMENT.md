# دليل البيئة والتشغيل — Nasr1

## 1. حدود البيئة

- المستودع المرجعي الوحيد: `Report-Engainall/Nasr1`.
- استخدم مشروع Supabase للتطوير/الاختبار منفصلًا عن الإنتاج عند تشغيل التطبيق أو اختبارات الكتابة.
- ملف `.env.example` يحتوي أسماء متغيرات عامة/فارغة فقط، ولا يحتوي مفاتيح أو بيانات دخول.
- لا يمكن اعتبار رابط Lovable تاريخي أو نجاح CI دليلًا على نشر الإنتاج أو مزامنته.

## 2. إعداد تطبيق الويب

ينشئ العميل في `src/integrations/supabase/client.ts` عميل Supabase من:
- `VITE_SUPABASE_URL`
- `VITE_SUPABASE_PUBLISHABLE_KEY`

ويستخدم SSR بديلَي الخادم `SUPABASE_URL` و`SUPABASE_PUBLISHABLE_KEY` إذا غابت القيم العامة أثناء التهيئة. احفظ الملفات المحلية في `.env` غير المتعقب في Git، واضبط المتغيرات نفسها في بيئة البناء/النشر المخوّلة.

**ممنوع:** `SUPABASE_SERVICE_ROLE_KEY` أو مفاتيح مزود الذكاء الاصطناعي أو أسرار العامل في متغير `VITE_*` أو ملفات الواجهة أو سجلات البناء. المفتاح القابل للنشر ليس بديلًا عن RLS أو التحقق من الدور والمؤسسة في RPC.

## 3. وظائف Supabase الخادمية

بيئة Supabase Edge Functions تزودها المنصة عادةً بـ`SUPABASE_URL` و`SUPABASE_ANON_KEY` و`SUPABASE_SERVICE_ROLE_KEY`. لا تنسخ مفتاح الخدمة إلى العميل. الوظائف التالية لها حدود اعتماد منفصلة:

| الوظيفة | المتطلبات الخاصة |
|---|---|
| `outbox-worker` | `OUTBOX_WORKER_SECRET`، مع تمرير السر في ترويسة `x-outbox-worker-secret` للعامل المخوّل فقط. |
| `async-export-worker` | `ASYNC_EXPORT_WORKER_SECRET` لوضع العامل المخوّل؛ وضع المستخدم لا يجوز أن يتجاوز RPC ذات النطاق الشخصي. |
| `ai-gateway` | مفاتيح الموفر الاختيارية مثل `AI_OPENAI_COMPATIBLE_API_KEY` أو `AI_GEMINI_API_KEY` ومعدلات التكلفة إذا تم اعتماد الموفر. لا يتطلب الاختبار المحلي موفرًا مدفوعًا؛ عند غياب الإعداد يجب إبقاء الحالة fallback/غير متاح بصدق. |
| `async-export-download` و`product-image-upload` | اعتماد المستخدم وتفويض قاعدة البيانات؛ لا تعرّض مفتاح الخدمة في الطلب أو المتصفح. |

أضف الأسرار عبر إعدادات Supabase المصرح بها أو مخزن أسرار البيئة. لا تحفظ قيمة فعلية في Git، ولا تطبعها في السجلات. لا تُفعّل أسرار العامل قبل إعداد العامل الذي سيستعملها.

## 4. قاعدة البيانات والاختبار

- الإصدار المستهدف لقبول قاعدة البيانات في CI هو PostgreSQL 17.
- `npm run test:db` يشغّل اختبارات SQL وRLS/RPC على قاعدة اختبار؛ متغير `TEST_DATABASE_URL` يجب أن يشير إلى قاعدة محلية/معزولة مثل `aghbari_test`.
- لا تشغّل المهاجرات أو اختبارات الكتابة على الإنتاج. لا تستعمل بيانات عملاء حقيقية أو أسرار الإنتاج في بيئة الاختبار.
- أوامر التطبيق: `npm run dev`, `npm run test`, `npm run lint`, `npm run typecheck`, `npm run build`.
- CI الحالي يحتوي اختبارات قبول إضافية مستقلة، منها PostgreSQL 17 وPlaywright. لا تعتبر نجاح خطوة واحدة إثباتًا لجميع المسارات أو لكل SHA.

## 5. الاختبارات الخارجية والاستعادة

- اختبار حسابات العملاء المستضافة لا يعمل إلا مع اعتماد غير إنتاجي مستقل، ومستخدمين اصطناعيين في مؤسستين مختلفتين، وتأكيد صريح بأن الكتابة غير إنتاجية. إذا لم تتوفر هذه المتطلبات فالنتيجة `BLOCKED_EXTERNAL` أو `SKIPPED` وليست نجاحًا.
- استيراد/مزامنة Onyx Pro الحي، أو إرسال WhatsApp Business API، يتطلب بيئة هدف معتمدة، واعتمادًا مخوّلًا، وطلبًا فعليًا واستجابة/معرفًا خارجيًا. التصدير المحلي ولقطة محفوظة لا يثبتان قبولًا أو مزامنة حية.
- اختبار استعادة PostgreSQL معزول لا يثبت جاهزية استعادة الإنتاج ولا يبرر ادعاء RTO/RPO للإنتاج.
- قبل أي نشر: راجع الفرق، المهاجرات وRLS/RPC، نتائج Core وP2 على SHA واحد، موافقة المراجع المطلوبة، ثم تحقق من SHA المنشور فعليًا. لا تدّعِ `PRODUCTION_PROVEN` دون دليل نشر وتشغيل حقيقي.
