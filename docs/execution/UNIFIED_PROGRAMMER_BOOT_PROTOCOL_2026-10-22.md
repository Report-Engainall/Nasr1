## 1. القرار الحاكم

الوثيقة الأصلية هي أساس النطاق الوظيفي ومعايير المنتج. التحسينات الهندسية اللاحقة الواردة هنا إضافات إلزامية ترفع مستوى الأمان والموثوقية وقابلية التشغيل، ولا تستبدل المتطلبات الأصلية ولا تبرر إلغاء وظيفة أو إنشاء واجهة شكلية. عند وجود تعارض، تُتبع أحدث تعليمات صريحة اعتمدها المالك، مع الإبقاء على الخيار الأكثر أمانًا وصحة للبيانات. لا تُخفف صلاحيات أو قيود أو اختبارات من أجل تمرير البناء.

الغاية هي إكمال متجر الأغبري كوحدة تشغيلية موحدة: متجر B2B، الإدارة، المخزون، المحاسبة، بيانات Onyx، الاستيراد والتصدير، التقارير، الذكاء الاصطناعي، المهام، التكاملات، التشغيل والتعافي. المطلوب مسارات حقيقية من الواجهة إلى الخدمة وقاعدة البيانات والصلاحيات والتدقيق والاختبار، وليس مجرد وجود مكونات أو ملفات.

## 2. الإقلاع الحي — دون إعادة عمل مكتمل

قبل أول تعديل في كل جلسة:

1. اقرأ الوثيقة الأصلية والقسم المتصل بالمهمة فقط.
2. اقرأ مؤشر الحالة التنفيذية الديناميكي الوحيد والمصفوفة الحية للقبول من المستودع. المؤشر يحدد نقطة الدخول التالية؛ المصفوفة تحفظ كل الأعمال المتبقية. لا تنشئ مؤشرًا ثانيًا.
3. اقرأ GitHub مباشرة: رأس `main`، فروع العمل، PRs المفتوحة، الملفات المتغيرة، آخر commit لكل فرع، ونتائج Actions المطابقة لكل SHA. لا تستخدم التقرير القديم بدل الحالة الحية.
4. افحص الفرع الذي ستتابع منه: آخر SHA محفوظ، الفرق عن `main`، وهل التغيير موجود أصلًا في فرع أو PR آخر. إن توفرت جلسة محلية، افحص أيضًا `git status` و`git diff`؛ لا تدّعِ فحص تغييرات محلية من خلال GitHub وحده.
5. حدّد أول فجوة مفتوحة ذات أولوية لم تُعالج بالأدلة. لا تعِد قراءة الأرشيفات أو تحليل المصادر السابقة أو إعادة اختبار SHA قديم بلا عيب جديد محدد.

عند اختلاف مؤشر الاستئناف عن GitHub، اعتمد الحالة الحية، ثم صحّح المؤشر في فرع عمل بعد إثبات التقدم. لا تُسجّل النجاح لمجرد محاولة إنشاء commit أو تعديل ملف؛ يجب أن يكون التغيير محفوظًا ويمكن قراءته من الفرع.

## 3. تقسيم المسؤولية الملزم

### P2 — البناء والتنفيذ والإصلاح

P2 هو منفذ التغييرات البرمجية في هذه المرحلة. يختار أول عمل مفتوح، يسجل ملكية المسارات المشتركة، ينفذ التغيير الفعلي، يضيف الاختبارات المناسبة، يقرأ نتائج التشغيل، يصلح السبب الجذري، يحدّث الحالة الحية بعد تقدم موثق، ثم ينتقل تلقائيًا إلى المهمة المفتوحة التالية. لا ينتظر P2 مراجعة P1 لعمل مستقل لا يتعارض مع مسارات أخرى.

قبل تعديل ملف مشترك، اقرأ الفروع وPRs المفتوحة وسجّل في سجل التنسيق: Task ID، الملفات الدقيقة، المالك الوحيد، فرع العمل وSHA الأساس، الملفات المستثناة، الاختبارات المطلوبة، وشرط تحرير القفل. لا تُحرر القفل إلا بعد الدمج والتحقق من الرأس اللاحق.

### P1 — التحقق المستقل فقط

P1 مدقق مستقل، وليس منفذ كود موازٍ. لا يكتب كودًا ولا يعدّل ملفات العمل المحجوزة لـP2. يتحقق من الرأس الدقيق الذي سلّمه P2، ويعيد الاختبارات ذات الصلة بطريقة مستقلة قابلة لإعادة الإنتاج، ويربط النتيجة بـSHA وActions. إذا وجد خللًا، يسلّم: الملف والسطر، السبب الجذري، خطوات إعادة الإنتاج، الاختبار الفاشل، والدليل/السجل. يعالج P2 الخلل ثم يعيد P1 التحقق من SHA الجديد.

لا يُعد نجاح CI أو اختبار قاعدة البيانات إثباتًا لاختبار المتصفح أو الاتصال بمزود خارجي أو نجاح الإنتاج. لا تُغلق المهمة اعتمادًا على عبارة عامة مثل PASS دون رابط وSHA يطابقان الكود المعني.

## 4. الإضافات الهندسية التي تبقى إلزامية فوق الوظائف الأصلية

### أ. الهوية والبيانات والتكامل

- مصدر حقيقة واحد للطلبات والمخزون والدفاتر التشغيلية، وربط السجلات المستوردة بمصدرها ومفتاحها الخارجي ومعرّف الدفعة وبصمة المحتوى وإصدار التحويل.
- التكامل مع Onyx Pro جزء من النظام، لا شاشة تحليل منفصلة. احفظ external IDs وsource/tenant IDs وحالة المطابقة وأسباب التعارض وآخر محاولة مزامنة ونتيجتها. افصل بوضوح بين لقطة مستوردة، ومحاولة مزامنة، ونجاح حي مثبت بطلب واستجابة فعلية.
- ملف Onyx الهدف له عقد إصدار ثابت من 27 عمودًا، مع الحفاظ على ترتيب الأعمدة والأصفار البادئة كنصوص، وخلايا غير المتاح فارغة، وحماية الصيغ، وتسجيل بصمة التصدير وإصدار القالب. توافق الهدف لا يُدّعى قبل قبول فعلي موثق من بيئة Onyx مصرح بها.

### ب. المعاملات والتدقيق والتزامن

- العمليات التجارية المهمة تنتج أحداثًا محفوظة ضمن المعاملة عبر Transactional Outbox؛ معالجة الأحداث والمستهلكات وإعادة المحاولة آمنة عند تكرار التسليم.
- استخدم idempotency على مستوى قاعدة البيانات/الخدمة للطلبات والاستيراد والتصدير والقيود والمزامنة، مع رفض إعادة استخدام المفتاح لحمولة مختلفة. أثبت سباقات التزامن بجلسات قاعدة بيانات مستقلة، لا بمحاكاة متسلسلة فقط.
- RLS وgrants وفحص المؤسسة والدور من جهة الخادم هي حد الأمان. كل كتابة حساسة تسجل الفاعل والمؤسسة والمصدر والنتيجة في audit. لا تسمح بنجاح وهمي عند إرجاع صفر صفوف، أو عند فشل RPC، أو عند رفض الصلاحية.

### ج. المخزون والنقل والجرد

- معاينة ثم تطبيق ذري تحت قفل؛ تحقق من حداثة اللقطة وبصمة المصدر والأرصدة وسجل الحركات، وعزل المؤسسة والمستودع، وحماية الكميات المحجوزة، ومنع المخزون المتاح السالب.
- عمليات التراجع تعويضية وتضيف حركة تدقيق؛ لا تمحُ الحركات، ولا تسمح بالتراجع فوق حركة أحدث.
- اختبر stale preview، والتكرار، والكتابة المتزامنة، وتعارض المستودعات، ونقص الصلاحية، والعزل بين المؤسسات. لا تغلق البند باختبار happy-path فقط.

### د. الاستيراد والتصدير وجودة البيانات

- احتفظ بمسار موحد للرفع والتجهيز واكتشاف الأعمدة والربط والتحقق والمعاينة والحفظ والاستئناف والمطابقة؛ لا تنشئ pipeline ثانيًا.
- أعد الاختبارات العدائية لحقن CSV/XLSX، وحدود الملفات والصفوف، وصحة التقويم والتواريخ، وبصمة الملف، وidempotency، والحفاظ على الأكواد والأصفار البادئة والقيم الرقمية السالبة كأرقام صحيحة النوع.
- يجب أن يوضح DQS أسباب الرفض ومستوى الجودة؛ لا تتحول القيمة المجهولة إلى صفر، ولا يسمح بدمج جزئي غير موضح أو تكرار الدفعة.

### هـ. الطلبات والعملاء والخصوصية

- تسلسل حالات الطلب خاضع لآلة الحالات وقيود قاعدة البيانات، والطلب وخطوطه ولقطة أسعاره مترابطة ذريًا ومصدرية.
- خصوصية الأسعار تُضبط منفصلًا حسب السطح: بطاقات/تفاصيل المنتجات، السلة، مراجعة الطلب، سجل العميل والفاتورة. لا تعرض مبلغًا إلا عند تفعيل إعداد ذلك السطح ووجود استجابة server-side سليمة وحديثة ومطابقة؛ أي خطأ أو حمولة ناقصة أو sentinel صفري يخفي القيمة ولا يعرض صفرًا أو يكشف تكلفة أو هامشًا أو سعر شريحة أخرى.
- الدعوات وتفعيل حساب الشركة وتغيير الأدوار والتحقق عبر المؤسسات تتطلب اختبارات منع الوصول غير المصرح به على مستوى الخدمة وقاعدة البيانات.

### و. المحاسبة والمردودات والطباعة ومركز المهام

- لا تنشئ دفتر أستاذ أو أرصدة نقدية موازية. القيود متوازنة ومصدرية ومقيدة بالمؤسسة والدور ومفتاح منع التكرار والتدقيق. التحصيلات والتخصيصات والأرصدة المتأخرة والعملات تستند إلى السجلات المحفوظة، لا إلى بيانات تجريبية أو أرقام مختلقة.
- دورة المردود تتضمن الطلب والمراجعة والاستلام الفعلي وحالة الكميات والإشعار الدائن المرتبط بالمستند المصدر؛ لا تجعل إنشاء المسودة ترحيلًا أو ردًا نقديًا تلقائيًا.
- مهام التشغيل تتولد من أحداث أعمال محفوظة بمعرف مصدر ثابت، وتمنع تكرار مهام المصدر نفسه. الطباعة تتقيد بالبيانات المسموحة والفلاتر والدور والمؤسسة والصفحات؛ تحقق من الفاتورة وكشف الحساب والإشعار الدائن ومخرجات المهام.

### ز. الذكاء الاصطناعي والتقارير

- استخدم بوابة مزودين قابلة للتبديل، وإمكانات مجانية أو محلية حيث يمكن، مع fallback قاعدي عند فشل المزود أو انتهاء الحصة، وسقوف استهلاك وحدود زمنية وإعادة محاولة مضبوطة.
- سجل قياسات الاستخدام المرصودة منفصلة عن التقديرات؛ القيم غير المعروفة تبقى NULL/غير معروفة. لا تحفظ مفاتيح أو أسرارًا أو prompts/outputs حساسة في سجلات الاستخدام، ولا تخلط بيانات المؤسسات.
- التوصية يجب أن تبين الأدلة والافتراضات والقيود والمالك ومقياس التحقق. لا تختلق قيمة أو سببًا أو أثرًا أو نسبة ثقة.

### ح. PWA والتكامل والتعافي والتشغيل

- العمل دون اتصال للقراءة من نسخة مؤقتة فقط؛ يمنع اعتماد الطلبات أو حركات المخزون أو القيود المالية دون اتصال. تُعرض حالة الاتصال ووقت آخر تحديث بوضوح.
- WhatsApp عبر واجهة WhatsApp Business الرسمية المصرح بها فقط؛ لا تُسجل الرسالة على أنها أُرسلت قبل معرف/استجابة مزود فعلية. عند غياب الاعتماديات تبقى `BLOCKED_EXTERNAL` مع السبب، بينما تستمر الاختبارات والعمل المستقل.
- اختبر النسخ الاحتياطي والاستعادة في قاعدة معزولة فقط، وقارن توقيعات المخطط والسياسات والمحفزات وRPCs والبيانات الحرجة. سجّل بصمة الأرشيف والمدة المقاسة؛ أي قيم P95/RTO/RPO غير المقاسة تبقى `NOT RUN`.

## 5. ترتيب التنفيذ وقاعدة عدم الهدر

- اتبع ترتيب الأولوية في الوثيقة الأصلية: أمن وصحة البيانات، ثم التكامل والتشغيل، ثم التحليلات والذكاء الاصطناعي، ثم تحسين العرض.
- استخدم صفوف المصفوفة المفتوحة أو الجزئية أو غير المثبتة فقط. الصف المغلق بدليل صحيح لا يعاد بناؤه. إذا تغير SHA أو ظهر regression جديد، أعد فقط الاختبارات اللازمة للرأس الجديد والنطاق المتأثر.
- لا تخلط مهامًا مستقلة في commit واحد، ولا تجعل فشلًا غير تابع يوقف مهمة أخرى.
- لا تعدّل `main` مباشرة، ولا تستخدم `reset` أو `clean` أو `force-push`، ولا تنشئ تطبيقًا أو قاعدة بيانات أو مشروعًا موازيًا. لا تستخدم بيانات إنتاج للاختبار أو خدمة مدفوعة كشرط للتشغيل.
- لا تعتبر وجود صفحة أو ملف أو نجاح build اكتمالًا. لا تستخدم بيانات وهمية أو تستنتج مزامنة حية أو قبولًا خارجيًا من snapshot أو اختبار داخلي.

## 6. سلم الإثبات والإغلاق

لكل Task ID، حدّد الحالة كلًا على حدة:
- `IMPLEMENTED`: التغيير مكتوب في فرع محفوظ.
- `INTEGRATED`: الشاشة والخدمة وDB/RPC والصلاحيات متصلة فعليًا.
- `TESTED_EXACT_SHA`: الاختبارات المطلوبة نجحت على SHA المطابق.
- `BROWSER_PROVEN`: اختبار متصفح حقيقي على المسار المقصود ونتيجته محفوظة.
- `PRODUCTION_PROVEN`: دليل إنتاجي مصرح به موجود فعلًا؛ لا تنفذ تغييرات إنتاجية للحصول عليه.
- `NOT RUN` / `BLOCKED_EXTERNAL`: هما الوصف الصحيح للاختبار الذي لم يعمل أو يتطلب اعتمادًا خارجيًا غير متاح.

لكل تسليم: Task ID، السبب الجذري، التغيير الفعلي، الملفات، SHA، الاختبارات ونتائجها، روابط Actions المطابقة، العيوب المتبقية، والحالة/المسؤول التالي. حدّث مؤشر الاستئناف بعد تقدم فعلي مثبت، ثم انتقل مباشرة إلى الفجوة التالية ذات الأولوية.

## 7. نقطة البدء لهذه الجلسة

أعد قراءة GitHub الآن قبل أن تعتمد أي قيمة أدناه. عند إنشاء هذا البروتوكول، كان رأس `main` المرصود `bf06c73226033da8e4f81e24981eb64e6e7fca99`، وكان فرع اختبار تزامن مصالحة المخزون قد أضيف عليه سكربت قبول بجلسات PostgreSQL مستقلة، ولم يكن قبول CI النهائي لهذا الفرع مثبتًا. افحص الرأس الحي والفرق والحالة والنتائج أولًا؛ واصل من آخر تغيير محفوظ فقط. لا تفترض أن هذه الجملة بقيت أحدث حالة عند تشغيل الرسالة لاحقًا.

**التكليف النهائي:** P2 يبني ويصلح ويدمج عبر PRs. P1 يتحقق استقلاليًا ويقدم دليلًا قابلاً لإعادة الإنتاج. الوثيقة الأصلية تحدد ما يجب أن يفعله النظام؛ الإضافات الهندسية أعلاه تحدد مستوى الأمان والموثوقية الذي يجب أن يحققه أثناء ذلك. يستمر العمل حتى إغلاق جميع المتطلبات بالأدلة، لا حتى اكتمال تقرير أو مهمة واحدة.
