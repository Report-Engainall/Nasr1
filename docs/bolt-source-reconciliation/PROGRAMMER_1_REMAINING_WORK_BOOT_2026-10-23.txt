## 1. التكليف والحدود

نفّذ الكود والربط والاختبارات، ولا تكتفِ بتقرير أو بإنشاء صفحة شكلية. أكمل النواقص المثبتة في التجارة وواجهات العميل والإدارة التجارية وفجوات دمج المصادر التي يملكها P1. استمر إلى المهمة التالية تلقائيًا ما دام هناك مسار مستقل قابل للتنفيذ.

- لا تعِد بناء التطبيق ولا تنشئ مشروعًا أو قاعدة بيانات أو محركًا موازيًا.
- لا تكتب مباشرة إلى main، ولا تستخدم reset أو clean أو force-push، ولا تحذف أدلة تاريخية.
- افحص HEAD والـPRs وCI الحية عند البداية، ثم عد فقط للمسارات المتأثرة. SHA قديم ليس دليلًا على الرأس الحالي.
- قبل لمس ملف مشترك، راجع الملفات المتغيرة في كل PR مفتوح وسجّل task ID والمالك الوحيد والمسارات وbase SHA والاختبارات وشرط فك القفل في WORK_COORDINATION.md. لا تحرر ملفًا يحرره P2.
- العربية RTL هي الافتراضية؛ الواجهة متجاوبة ومهيأة للوحة المفاتيح وحالات التركيز وإتاحة الاستخدام.
- ممنوع mock أو زر بلا فعل أو نجاح معلن قبل تأكيد الخادم. لا تجعل الواجهة سلطة على السعر أو المخزون أو الصلاحيات أو حالة الطلب.
- لا تشغّل جولات Bolt New الشاملة الآن؛ اختبار الواجهات المجمع مؤجل حتى يكتمل كود P1 وP2.

## 2. مصادر العمل والإقلاع

اقرأ هذه الرسالة، الخطة، المواصفة الأصلية، سجل المتطلبات، المصفوفة، تقرير P1، سجلي المصدر، وPR #31/diff الخاص به قبل تحديث أدلة P1. لا تعتمد وصفًا قديمًا على أنه حقيقة حية.

تابع فقط صفوف المصدر المفتوحة أو غير المحسومة فعلًا. لا تعِد فحص أو إدراج صفوف تحمل قرارات مبررة مثل ALREADY_PRESENT_EXACT أو ALREADY_PRESENT_BETTER أو DUPLICATE_PROVEN أو INCOMPATIBLE_WITH_EVIDENCE أو KEEP_AS_REFERENCE إلا عند ظهور دليل regression جديد.

ابدأ من أول task source غير محسوم حسب السجل الحالي، مع مراجعة دلالات order-input والميزات المصدرية المفتوحة. تقرير P1 السابق ذكر SRC-011 / migration 0011، لكن يجب التحقق من الحالة الراهنة أولًا؛ لا تعِد عملًا اكتمل على main. لكل قرار دوّن مستودع المصدر وref/SHA والمسار وblob وبصمة الهدف والسبب والاعتماديات والاختبار والنتيجة الدقيقة.

حلّ فروق الجرد بوصفها مشكلتين منفصلتين: 2,329 إدخالًا في شجرة المصدر مقابل 2,044 ملفًا في تقرير الاستخراج؛ و2,044 ملفًا مقابل 2,011 blob موثقًا (33 مسارًا غير مفسر). لا تخمّن المفقود ولا تعاود تنزيل/فك أرشيف حُسم. Git blob SHA-1 ليس SHA-256 لأرشيف ZIP. المستودعات المانحة للقراءة فقط؛ جميع تغييرات التنفيذ داخل Nasr1.

## 3. إكمال جميع شاشات وأفعال العميل

طابق شجرة المسارات الحية مع مصفوفة القبول، ثم تتبّع كل شاشة وفعل من route إلى component ثم service/command ثم RPC/API ثم schema/RLS/tenant/role ثم audit/idempotency والاختبارات. نفّذ النقص المؤكد فقط في المجالات التالية:

1. الرئيسية والكتالوج والتصنيفات والبحث والاقتراحات والفلاتر والفرز والصفحات وحالات عدم وجود نتائج.
2. تفاصيل المنتج والصور والوحدة والكود والتوفر؛ البحث بالاسم/SKU/الباركود حيث يدعمه العقد.
3. المفضلة والمقارنة والقوالب الشرائية وإعادة الطلب والباركود، مع حفظ آمن خاص بالمستخدم/المؤسسة.
4. كمية السلة وتوحيد أسطر الصنف ومنع التكرار، ووحدات القطعة/الكرتون/MOQ ومضاعفات الطلب وفق إعدادات الصنف.
5. السلة والـcheckout ومراجعة الأسعار واختيار العنوان وإرسال الطلب وتأكيده ورقمه وسجل الطلبات وتفاصيلها.
6. عروض الأسعار/RFQ حيث تكون ضمن المسارات الحالية: إرسال فعلي وحالة محفوظة وتدقيق ورفض success كاذب.
7. الملف التجاري والعناوين وملف الشركة والأعضاء والعضويات والدعوات والقبول والإلغاء وانتهاء الصلاحية، مع منع قراءة شركة/عضوية غير مصرح بها.
8. حالات الجلسة المنتهية، التحميل، الفراغ، الخطأ وإعادة المحاولة، التحقق من المدخلات، الاتصال الضعيف، والتأكيد قبل الأفعال المدمرة.

السعر والخصم والكمية المتاحة والائتمان وحالة الطلب سلطة خادمية. استعمل idempotency ضد النقر المتكرر، ولا تنشئ طلبًا مكررًا بعد timeout. لا تعتمد إجماليًا محسوبًا في المتصفح، ولا تعتبر فشل الاستجابة دليلًا على عدم الحفظ دون فحص مرجع العملية.

## 4. الإدارة التجارية

أكمل الوظائف الناقصة في هذه الشاشات على الموجود، دون إنشاء بديل:

- المنتجات: القائمة والبحث والتصفية والإنشاء والتعديل والأرشفة، التحقق من الحقول والصور وأحجامها، رسائل الخطأ والتأكيد.
- التصنيفات: إنشاء/تعديل/أرشفة/إعادة تسمية، منع الأسماء المكررة وحفظ علاقات parent/code/order/IDs.
- العملاء والشركات والأعضاء والموظفون والأدوار والدعوات، مع صلاحيات واضحة وتحقق خادمي لكل أمر.
- إعدادات التسعير والعروض/الاقتباسات وقائمة الطلبات وتفاصيلها ومراجعتها وانتقالات الحالة المسموحة والتصدير المصرح به.
- خرائط صلاحيات المؤسسة والأدوار: إخفاء زر ليس بديلًا عن رفض الخادم؛ لا ترسل أصلًا بيانات غير مصرح بعرضها.

## 5. خصوصية السعر والسلة والطلبات

افحص عمل PR #12 والتغييرات المدمجة على main قبل التحرير. اربط إظهار السعر في بطاقات المنتجات والتفاصيل والمفضلة والمقارنة والسلة والـcheckout ومراجعة الطلب وسجل الطلب/الفاتورة بالإعداد المستقل لكل موضع وباستجابة الخادم المعتمدة.

اختبر حالات: مسموح، مخفي، NULL، sentinel صفري غير صالح، فشل RPC، حمولة مشوهة، جلسة منتهية، وتبدل الدور/المؤسسة. عند منع العرض، يجب ألا توجد بيانات مالية في markup أو payload غير اللازم. فشل الإعداد أو غياب الاستجابة يفشل مغلقًا.

لا تعد بناء أساس خصوصية السعر أو حماية السلة/checkout المثبت. لا تعدّل src/lib/api.ts أو RPC/migrations المالية أو كتابة حالة الطلب المملوكة لـP2. PR #56 هو مسار P2 لتأكيد أثر تحديث حالة الطلب؛ P1 يستطيع لمس واجهة AdminOrders/خياراتها فقط بعد التنسيق مع #56/#61 والتأكد من عدم وجود تعديل متداخل.

## 6. ضوابط الجودة والأمان

- حالات loading/empty/error/retry/validation/disabled/unauthorized/offline/stale واضحة وغير مضللة.
- لا تسرب بيانات شركة أخرى أو بيانات مالية أو فئة سعرية أو رموز دعوة. لا تعرض الأسرار أو بيانات شخصية غير لازمة في الخطأ أو الرابط أو السجل.
- تأكيد خادمي لكل كتابة؛ منع التقديم المتكرر؛ audit عند الأفعال الحساسة؛ لا اعتماد على localStorage في الهوية/السعر/المخزون.
- كل شاشة يجب أن تعمل مع صلاحياتها الفعلية، لا مع حساب إداري فقط.
- لا تنشئ محرك تسعير أو طلبات أو استيراد جديدًا إذا كان النظام الحالي يغطي العقد.
- لا تستخدم بيانات إنتاج أو فواتير/أرصدة مختلقة، ولا تغيّر RLS لتجاوز فشل harness.

## 7. الاختبار والإغلاق

بعد كل دفعة نفّذ اختبارًا مركزًا مناسبًا:
1. Unit/component لنتيجة العرض والسلوك والحالات الحدية.
2. Service/contract لاختبار الحمولة والاستجابة والأخطاء.
3. PostgreSQL/RLS معزول عند تغيير عقد/صلاحية، بالتنسيق مع P2.
4. Core CI/build على الرأس النهائي عند الحاجة، مع رابط run وSHA والنتائج.

إذا فشل Playwright قبل بدء التطبيق بسبب Supabase أو سحب الصور أو غياب بيانات اعتماد، سجّل الخطأ الحقيقي كـBLOCKED_EXTERNAL/NOT_RUN، ولا تسجله PASS ولا تخلطه مع فشل المنتج. أصلح الفشل الحقيقي داخل التطبيق باختبار مركز. لا تنفّذ مراجعة واجهة شاملة عبر Bolt الآن.

لا تغلق أي row في المصفوفة إلا بدليل يطابق SHA. تسليم كل دفعة يجب أن يضم Task ID والسبب الجذري والملفات المتغيرة ومصدر/قرار النقل والاختبار ونتيجته وSHA ورابط CI والمسارات NOT_RUN/BLOCKED_EXTERNAL.

حدّث تقرير P1 وسجلي المصدر فقط عندما توجد أدلة جديدة. حدّث صفوف P1 في المصفوفة بعد قفل الملف المشترك والتأكد أن P2 لا يحرره بالتزامن. لا تعدل CURRENT_EXECUTION_STATE.md أو تقارير/سجلات P2.

## 8. تعريف الانتهاء

تُغلق مهمة P1 عندما تكون الشاشة/الفعل متصلة end-to-end، الصلاحيات والـtenant مفروضة خادميًا، حالات الفشل والنجاح حقيقية، الاختبارات المطلوبة ناجحة على SHA محدد، والدليل مضاف للسجل. ما يحتاج credentials أو صلاحيات خارجية يبقى BLOCKED_EXTERNAL. بعد كل دفعة تابع مباشرة إلى أول فجوة P1 مثبتة تالية؛ لا تنهِ التنفيذ بتقرير فقط طالما توجد مهمة قابلة للتنفيذ.
