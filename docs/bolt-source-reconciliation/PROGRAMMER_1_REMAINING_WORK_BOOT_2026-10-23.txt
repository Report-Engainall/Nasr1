## 2. المطلوب الفعلي

### A. إنهاء فجوات المصدر فقط
- استكمل صفوف المصدر غير المحسومة في SOURCE_INTEGRATION_LEDGER.csv وREADY_TO_REUSE_FILE_AUDIT.csv، وليس الصفوف ذات قرار موثق مثل ALREADY_PRESENT_BETTER أو DUPLICATE_PROVEN أو INCOMPATIBLE_WITH_EVIDENCE أو KEEP_AS_REFERENCE.
- ابدأ من SRC-011 ودلالات مدخلات الطلبات/الميزات المرشحة التي ما زالت مفتوحة في السجل. قارن semantics المصدر مع كود Nasr1 الحالي، ثم ادمج الوظيفة المفيدة فقط عبر عقد Nasr1؛ لا تنسخ RPC/SQL أو React Router قديمًا كما هو.
- حلّ فروقات جرد المصدر المسجلة بالأدلة: 2,329 مدخلًا في شجرة المصدر مقابل 2,044 في تقرير الاستخراج، وكذلك 2,044 ملفًا مقابل 2,011 blob موثّقًا (33 مسارًا غير مفسر). تعامل معها كفروقات مستقلة حتى تتم المطابقة؛ لا تخمن الملفات المفقودة ولا تكرر تنزيل/فك الأرشيفات المحسومة.
- راجع أن source/target path والبصمة والسبب والاعتماديات والاختبار وحالة الإثبات مكتوبة لكل عنصر بقي مفتوحًا. لا تدّع إغلاقًا إذا بقي قرار بلا اختبار أو بلا تفسير.

### B. إكمال واجهات التجارة والعميل والإدارة التجارية
افحص كل شاشة/فعل من المسارات الحالية، ونفّذ النواقص المثبتة فقط:
- العميل: الكتالوج والبحث/التصنيفات وتفاصيل المنتج والمفضلة والمقارنة والسلة والـcheckout وتأكيد الطلب وسجل/تفاصيل الطلب وإعادة الطلب وعروض الأسعار/الاقتباسات والباركود والملف التجاري والعناوين وعضويات الشركة ودعواتها.
- إدارة التجارة: قائمة المنتجات وإنشاؤها/تعديلها، التصنيفات وإنشاؤها/تعديلها/أرشفتها، العملاء والشركات والأعضاء والموظفون/الأدوار، إعدادات الأسعار، قائمة الطلبات ومراجعتها وانتقالاتها والتصدير.
- خرائط كل شاشة وفعل: route → component → service/command → RPC/API → schema/RLS/role/tenant → audit/idempotency → tests. لا تعدّ الصفحة متصلة إذا كان زرها بلا فعل خادمي أو إذا قالت نجاحًا دون تأكيد نتيجة الكتابة.
- أغلق الحالات المرئية الضرورية: loading، empty حقيقي، error/retry، validation، disabled، unauthorized/permission denied، stale/offline، وحماية الإجراء التدميري. اجعل العربية RTL افتراضية ومتجاوبة مع لوحة مفاتيح وإمكانية وصول أساسية.
- لا تنشئ نموذج تسعير أو محرك طلبات أو مكوّنًا بديلًا إن كان الموجود يغطي العقد. لا تكسر سلطة الخادم على السعر والكمية والمخزون وحالة الطلب وtenant.
- راجع PR #12 الخاص بإعدادات إظهار الأسعار مقابل main الحالي وما اندمج من تدفقات السعر. لا تدمج فرعه القديم عميانيًا ولا تعِد ميزة موجودة؛ احمل فقط الفجوة المثبتة إذا بقيت.
- راجع PR #43 كتغطية لاختبار واجهة إدارة أدوار المؤسسة. لا تكرر backend/RPC الموجود. إذا كان الفشل قبل بدء التطبيق بسبب تهيئة Supabase أو سحب صور الحاويات، سجّله كحاجز بيئة، واستكمل التحقق بكود/اختبار مركز دون ادعاء browser proof.

## 3. ما يُعدّ منجزًا ولا يجوز تكراره

لا تعد إنشاء أو إعادة دمج ميزات مثبتة في الخطة المشتركة، ومنها التحويل المخزني متعدد المنتجات، حد بكسلات صورة المنتج، أساس خصوصية سعر البطاقات/التفاصيل، أساس تدفقات المرتجعات، أساس العضويات/الدعوات، محاسبة استلام المشتريات، مهام الشراء والاستلام، واختبار خصوصية السلة ومراجعة الطلب. تحقق من main الحالي إذا أثّر تغيير جديد على هذه المسارات؛ لا تكرر التنفيذ لمجرد أن تقريرًا قديمًا وصفه بأنه مفتوح.

لا تلمس عمل P2 الجاري في:
- Onyx/source-trace/sync evidence والمخزون/التراجع والتزامن.
- migrations/RPCs والحسابات والفواتير وكشوف الحساب/الإشعارات الدائنة/المصروفات والطباعة المالية.
- محرك الاستيراد/DQS وXLSX/CSV وAI gateway/usage وPWA/service worker وbackup/restore وP2 workflow.
إذا ظهر تداخل حقيقي، أنشئ طلب handoff واضحًا قبل التحرير؛ لا تتزامن الكتابة على ملف واحد.

## 4. حواجز الاختبار وBolt New

- لا تفتح مشروع Bolt ولا تصرف نقاطه الآن. لا تُنفذ جولات UAT يدوية أو إعادة Playwright شاملة مع كل دفعة.
- نفّذ فحوصًا سريعة ومحددة فقط عند تغيير الكود، خصوصًا unit/contract واختبار API أو PostgreSQL المعزول الضروري لإثبات العقد. أصلح الفشل الفعلي بدل تجاهله.
- فشل browser workflow قبل بدء التطبيق بسبب GHCR/image pull أو فحص بيئي لا يثبت خلل المنتج. سجّل السبب الحرفي ثم تابع العمل المستقل. لا تُرخِ RLS أو migrations أو قواعد البيانات لإرضاء harness غير مطابق.
- بعد اكتمال البرمجة من P1 وP2، تجمع كل اختبارات الواجهة في جلسة Bolt New واحدة لاحقة؛ لا تعلن BROWSER_PROVEN قبلها.
- لا تستخدم بيانات إنتاج أو حسابات/أرصدة/فواتير مختلقة، ولا تضع أسرارًا في Git.

## 5. التسليم المطلوب لكل دفعة

قدّم تغييرًا فعليًا قابلًا للمراجعة، وليس تقريرًا فقط:
- Task ID واضح، وأسباب اختيار الفجوة، والمسارات التي تغيرت، وأي مصدر/Blob قررت تكييفه.
- اختبار محدد تم تشغيله ونتيجته، ورأس SHA الذي يخصه، ورابط CI إذا توفر.
- قائمة قصيرة بالمسارات التي ظلت NOT RUN أو BLOCKED_EXTERNAL وسببها الحقيقي.
- حدّث صفوف المصدر ومصفوفة القبول وسجل P1 فقط بعد دليل. لا تعدّل CURRENT_EXECUTION_STATE أو ملفات P2.
- بعد كل دفعة، تابع تلقائيًا إلى أول فجوة أخرى مثبتة في نطاق P1. لا تطلب من المالك إعادة إرسال مواصفات أو ملفات موجودة في المستودع، ولا تنهِ الجلسة بخطة فقط ما دام هناك مسار مستقل قابل للتنفيذ.

**أولوية النجاح:** اكتمال فعلي للشاشات/الأفعال التجارية مع عقودها، توثيق مصدر دقيق، وعدم تكرار أي عمل مثبت.
