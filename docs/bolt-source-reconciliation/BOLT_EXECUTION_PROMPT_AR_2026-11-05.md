## 2. تفويض التنفيذ وطريقة العمل

أنت المنفذ التقني داخل Bolt. اتخذ القرارات الهندسية السليمة بنفسك، وافحص الموجود ثم نفّذ مباشرة. لا تكتفِ بخطة أو تقرير أو شاشة تجريبية. لا تطلب من المالك إعادة شرح المشروع أو كتابة قائمة الملفات أو إعطاء أسرار يمكن أن يوفرها Bolt من إعداداته. نفّذ دفعات كبيرة مترابطة، ثم اختبرها، ثم انتقل تلقائيًا إلى العمل التالي.

**الهدف التشغيلي هو أن يكون التطبيق بعد هذه الدفعة مبنيًا وظيفيًا بنسبة 90% على الأقل وفق بنود المصفوفة، بحيث لا يستهلك رصيد Bolt المجاني في إنشاء الواجهات من الصفر أو إعادة تخطيط المشروع، بل في تهيئة قاعدة البيانات، توصيل الخدمات الموجودة، إصلاح التوافق، تشغيل Preview، وتنفيذ اختبارات End-to-End حقيقية.** لا تخترع نسبة إنجاز؛ احسبها من عناصر المصفوفة التي اجتازت القبول فقط، واذكر الباقي بدليل.

ممنوع حذف ميزة أو شاشة أو محرك أو اختبار أو migration لمجرد تقليل حجم النقل. ممنوع إنشاء نسخة MVP مصغرة أو واجهات شكلية أو بيانات وهمية في مسارات الإنتاج. طوّر المحرك الموجود بدل إنشاء محرك ثانٍ.

## 4. استخدم Bolt Database المدمجة — دون تكلفة أو مزود خارجي

1. استخدم قاعدة البيانات المدمجة في **Bolt Cloud** ضمن المشروع الحالي. استخدم ما يتيحه Bolt فعليًا من PostgreSQL/database وAuthentication وFile Storage وServer Functions وSecrets وLogs.
2. لا تختر ربط Supabase خارجيًا ولا تطلب ترقية Pro/Teams. لا تستخدم Lovable أو Lovable Cloud أو إعدادات أو Preview أو Telemetry تخصه.
3. لا تفترض أسماء متغيرات البيئة أو endpoints ولا تنشئ مفاتيح وهمية. افتح مورد قاعدة البيانات في مشروع Bolt، تحقق من الوسائل الفعلية التي وفرها، ثم اضبط اتصال التطبيق بها. إذا كانت واجهة Bolt متوافقة مع Supabase JS فاثبت التوافق من البيئة؛ وإذا لم تكن، فأنشئ طبقة توافق آمنة باستخدام Server Functions/اتصال PostgreSQL الذي يتيحه Bolt.
4. لا تضع Service Role أو Database URL أو أي سر في متغير `VITE_*` أو JavaScript المتصفح. الأسرار في Bolt Secrets والوظائف الخلفية فقط.
5. لا تنقل عمليات الكتابة الحساسة إلى المتصفح ولا تستبدل RPC/المعاملات بعمليات CRUD متفرقة. يجب أن تبقى العمليات المالية والمخزنية ذرية، محمية، قابلة للتدقيق، وIdempotent.

## 5. توصيل قاعدة البيانات دون كسر العقود

افحص كل ملفات `supabase/migrations` وجميع المكونات المستخدمة، ثم أنشئ جردًا فعليًا يشمل:

- كل الجداول والعلاقات والمفاتيح والقيود والفهارس والتريغرز والأنواع والـ extensions.
- كل الدوال وRPC وتواقيعها وصلاحيات تنفيذها ومعاملاتها.
- كل RLS policies ونطاق المؤسسة/المستأجر tenant وحدود الأدوار RBAC.
- كل Buckets وسياسات القراءة والكتابة والملفات الخاصة.
- كل Edge Functions وServer Functions وQueues/Outbox وعمليات الإرسال.
- كل مسارات المصادقة والجلسات وتحديث الرمز وتبديل الحساب والخروج والاسترداد.

حوّل كل عنصر إلى Bolt-equivalent مثبت. لا تعتبر إنشاء الجداول وحده نقلًا مكتملًا. عند وجود ميزة PostgreSQL لا يدعمها Bolt بنفس الصورة، نفّذ بديلًا مكافئًا على الخادم، ثم اختبر النجاح والرفض وعدم وجود أي أثر جانبي عند الرفض. إذا لم يوجد بديل آمن، سجّل المانع الدقيق ولا تضعف الأمان.

**البيانات:** لا تفترض أن schema الجديد ينقل المستخدمين والعملاء والطلبات والأرصدة والمخزون وسجل القيود والملفات. لا تمسح أو تستبدل أي قاعدة بيانات موجودة. اعمل أولًا في قاعدة اختبار/بيانات Seed منفصلة. لا تنفذ ترحيلًا لبيانات إنتاج إلا بعد تحقق النسخ الاحتياطي والاستعادة والمطابقة والهوية الرسمية للمؤسسة.

## 6. أكمل التطبيق نفسه قبل الاكتفاء بالربط

افتح كل شاشة موجودة واختبرها كمسار عمل حقيقي. أصلح المكونات والأحداث والنماذج والتنقل والتحميل والخطأ وعدم وجود بيانات وانقطاع الاتصال والصلاحيات. لا تقبل أي زر غير موصول أو زر نجاح وهمي أو نموذج يغيّر الشاشة فقط ولا يحفظ البيانات.

يجب على الأقل إثبات هذه التدفقات في البيئة:

- زائر/عميل: التسجيل والدخول والخروج، استعراض المنتجات، البحث، تفاصيل المنتج، التسعير حسب الشريحة، السلة، حفظها، إتمام الطلب، إعادة المحاولة بعد انقطاع الرد، سجل الطلبات والفواتير وكشف الحساب والمرتجعات والمفضلة والمقارنة وإعادة الطلب.
- إدارة: إنشاء/تعديل منتج وتصنيف، إدارة الأسعار والعميل والطلب، الأعضاء والأدوار، بيانات الشركة والتسليم، العمليات والموافقات.
- مستودعات: أمر شراء، استلام فعلي مرة واحدة، تحويل مخزون، جلسة جرد وحفظ الكمية والتصدير والطباعة دون تكرار الحركة.
- مالية: تسجيل دفعة وتخصيصها على فاتورة أو عدة فواتير، منع الزيادة غير المسموح بها، كشف الحساب، المصروفات، القيود، الميزان، التقارير والتصدير والطباعة.
- Onyx: استيراد وتحليل ومطابقة 27 عمودًا، معاينة الأخطاء والتكرارات، استيراد قابل للاستئناف، وتصدير مضبوط الصلاحيات.
- الذكاء والتشغيل: المهام اليومية ومساعد التاجر والتنبيهات والتحليلات والقرارات والتنبؤات والـ AI fallback المجاني. لا تستخدم APIs مدفوعة أو تنشئ مصروفًا دون إذن.
- PWA: الكاش للقراءة فقط. يمنع إنشاء طلب نهائي أو حركة مالية/مخزنية أثناء Offline.
- الملفات: التخزين الخاص، الصلاحيات، PDF/XLSX والطباعة وRTL والخطوط.

## 7. بوابات الأمان التي لا يجوز تجاوزها

- اختبر مستخدمين من مؤسستين مختلفتين؛ يمنع كل مستخدم قراءة/تعديل بيانات المؤسسة الأخرى.
- اختبر كل دور عميل وموظف ومحاسب ومدير وإدارة؛ رفض العملية يجب ألا ينشئ صفًا أو قيدًا أو حركة أو أثر تدقيق غير صحيح.
- أثبت إخفاء الأسعار والتكاليف والهوامش ومجاميع الشرائح الأخرى في DOM وNetwork/API وRPC وJSON وPWA وPDF وXLSX، لا في شكل الواجهة فقط.
- احفظ ضمانات تبديل الحساب وlogout وsession refresh وgeneration guard الموجودة بالفعل.
- اختبر idempotency وretries وعدم تكرار الطلب والدفع والاستلام والتحويل.
- أثبت اتزان القيود والحسابات وعدم تعديل التاريخ المحاسبي بالحذف؛ التصحيح بعكس/قيد تسوية.
- لا تعرض المفاتيح أو بيانات العملاء أو الرموز في المتصفح أو سجلات التشخيص.
- نفّذ Security Audit لقاعدة Bolt وفحص التطبيق كاملًا؛ لا تعتبر فحص قاعدة البيانات وحده تدقيقًا كاملًا.

## 8. إعداد البناء والتشغيل والاختبارات

تم تجهيز مصدر التطبيق في main ليعمل بدون غلاف Lovable:
- `vite.config.ts` يستخدم Vite/TanStack Start/Nitro/React/Tailwind وtsconfig paths بشكل صريح.
- أزيل `@lovable.dev/vite-tanstack-config` من `package.json` و`bun.lock`.
- أزيل Lovable preview auth bridge وتليمترية المحرر.
- أضيف تشخيص أخطاء عام لا يرسل الرسائل الخام أو stack أو بيانات العملاء لمزود خارجي.

لا تُعد هذه التغييرات اختبارًا ناجحًا. نفّذ في Bolt وعلى SHA واحد:
1. تثبيت الاعتمادات باستخدام Bun وقفل الاعتمادات دون استبدال `bun.lock` بملف npm.
2. TypeScript typecheck وESLint وVitest كاملًا.
3. فحوص SQL/migrations على نسخة اختبار PostgreSQL/Bolt فقط.
4. Vite dev/build/preview وتشغيل TanStack Start SSR.
5. اختبارات Playwright/Chromium لجميع مسارات العميل والإدارة والتدفقات المالية والمخزنية والتصدير.
6. اختبارات RLS/tenant/RBAC والرفض بلا أثر جانبي، والنسخ الاحتياطي والاستعادة.
7. اختبر عدم وجود أي اعتماد تشغيلي متبقٍ على `lovable` أو `lovable.dev` أو `__lovable` في build/runtime/imports. احتفظ فقط بذكر تاريخي في وثائق المصدر عند الحاجة.

إذا فشل فحص، عالج السبب ثم أعد الاختبار المتأثر والـ regression suite. لا توقف المهمة بعد فشل أولي، ولا تسجل PASS لعمل لم يمر.

## 9. سياسة الوقت والرصيد

- لا تنشئ المشروع من الصفر ولا تعِد بناء الشاشات التي توجد بالفعل.
- لا تستهلك الرصيد في خطة مطولة أو استكشاف مكرر أو استعراض تقرير بلا تنفيذ.
- افحص بنية التطبيق مرة واحدة بصورة منظمة، أنجز دفعة كبيرة، ثم انتقل إلى التالية.
- استخدم قاعدة Bolt المدمجة والخدمات المتاحة في الحساب الحالي. لا تفعل خطة مدفوعة أو ربطًا مدفوعًا أو auto-billing أو auto-recharge.
- لا تستخدم بيانات الإنتاج كبيانات اختبار.
- إذا كان نقص مورد من Bolt نفسه يمنع خطوة، انتقل إلى العمل المستقل التالي وسجّل المانع الدقيق دون إيقاف بقية الإنجاز.

## 10. تعريف التسليم المطلوب

لا تعلن الاكتمال بمجرد أن Preview يفتح. سلّم أدلة قابلة للتحقق تتضمن:

1. آخر SHA من main وSHA التطبيق الذي اختبرته فعليًا.
2. رابط Bolt Preview العامل، ونتيجة SSR/build.
3. اسم مورد Bolt Database ونوعه وحالة الاتصال، دون كشف أسرار.
4. قائمة المهاجرات والجداول والدوال والتريغرز والسياسات والتخزين والوظائف التي نُقلت واختُبرت.
5. عدد ملفات الاختبار والاختبارات التي مرت/فشلت/تخطيّت مع سبب كل تخطٍّ.
6. قائمة مسارات العميل والإدارة التي جرى فتحها وفحصها فعليًا.
7. نتائج tenant/RBAC/pricing privacy/idempotency/financial inventory acceptance.
8. نتيجة النسخ الاحتياطي والاستعادة والبيانات التي لم تُنقل إن وجدت.
9. نسبة الإنجاز المحسوبة من عناصر المصفوفة، لا تقديرًا لغويًا، وما بقي للوصول إلى 100%.
10. العوائق الدقيقة والقرار المطلوب من المالك فقط إن كان لا يمكن تجاوزه تقنيًا.

**النتيجة المطلوبة:** متجر الأغبري كامل البنية والواجهات والوظائف والمحركات، يعمل على Bolt Database وخدمات Bolt الفعلية، ومجتازًا لاختبارات E2E موثقة. أبقِ كل المنجز، لا تعِد البناء، ولا تتوقف عند خطة أو نموذج واجهات.
